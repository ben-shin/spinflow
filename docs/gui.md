# Spectrum workbench

This guide describes the 0.3.0b1 experimental beta; the previous v0.2.0 prerelease does not include the processing budget control described below. Use the versioned beta installation instructions or build its source as explained in the [Linux installation guide](../README.md#install-the-030b1-experimental-beta-on-linux).

On a Linux desktop, install the optional GUI and figures with `bash tools/bootstrap.sh --gui --plot`,
then run `.venv/bin/spinflow gui` from the project folder. Follow the
[Linux user-testing walkthrough](linux-user-testing.md) for a guided synthetic session. The workbench uses
the same `nmrnext` processing and file APIs as the command line. The selected
[laboratory-workflow protocol](laboratory-workflow-protocol.md) and
[results](laboratory-workflow-results.md) record the separate comparison gates.

## First run

1. Choose **1D demo** or **2D demo** for a synthetic, fully sampled acquisition.
2. Inspect the axes and select the real or imaginary quadrature channel above the plot. Channel labels follow the dataset's actual complex-axis order. The signed intensity is shown; negative peaks remain negative.
3. Set line broadening, zero fill and phase separately for each spectral axis; choose one backend for the complete recipe. Switching the selected axis retains its values; **All spectral axes** edits each changed setting across eligible axes and shows when current values differ. **Preview** computes the complete recipe without making it the current result. Changing a processing setting clears that preview. **Process** runs the recipe for all axes from the immutable original and makes the result current. **Reset to original** discards that result. For an already frequency-domain axis, **Crop frequency region** uses zero-based start-inclusive and stop-exclusive point indices.
4. Choose **Save current result…** for a spectrum file, **Save runnable workflow…** for a new folder containing the original native source and a CLI `workflow.json`, or **Save audit report…** for a JSON inspection record of operations, plan, axes and resolved processing history. The workflow reproduces the last applied result, rather than a preview or pending control edits. See the [Linux walkthrough](linux-user-testing.md) for exact replay commands.

To open an existing schema-1 CLI workflow, choose **Load ordered recipe…** and select its `workflow.json`. The workbench resolves the recipe input relative to that file, reads it under the current file-size guard, and checks the complete processing plan before changing the view. The **Ordered processing steps** list shows every operation in execution order, including sine windows, transposes, imaginary-channel discards, explicit references and phase. Double-click a step to edit its fields; transpose order accepts comma-separated axis IDs such as `a0, a1` or zero-based positions such as `0, 1`. **Edit complete operation JSON** exposes every supported parameter, including those absent from the quick controls. Add, remove and move actions validate the whole sequence. A failed edit leaves the pending and applied recipes intact. The quick controls are paused for an ordered recipe. **Start a new quick recipe** explicitly replaces only the pending recipe after confirmation; the applied result remains until Process.

**Save applied session…** creates a new folder with the source snapshot, runnable CLI workflow and versioned session record. It saves the applied recipe, backend, budget, selected analysis region and digest-linked reports. **Open saved session…** verifies the files and replays the recipe before replacing the current view. It restores the applied result and the same editable ordered steps. Pending edits and previews are excluded. Save and reopen operate on the source snapshot, so an original acquisition folder can later be moved. Existing destination folders are refused.

Set **Processing working-array budget (MiB)** before opening or processing data; it defaults to 256 MiB. The full-recipe preview and Process use that limit, and saved workflows and sessions retain the exact limit of the applied result even if the control is later changed. Opening also has a separate 1 GiB payload ceiling. The estimate covers working arrays, not all solver, backend or process memory, and is not an RSS limit. The analysis size limit remains separate; choose a bounded region on a large processed result. Header-only planning is unavailable for JCAMP-DX; convert it to native format with the CLI before opening it here.

The plot supports wheel zoom and drag pan. Frequency axes use ppm when calibrated and follow the usual descending NMR direction; time axes use milliseconds. For large arrays the display is sampled, and the footer says so. Processing and export always use complete data.

## Bruker and analysis controls

For a declared complex Bruker raw 1D or full-hypercomplex 2D acquisition with a recorded positive `GRPDLY`, **Correct Bruker digital filter** explicitly adds the versioned correction before windowing, zero fill and FFT. It is off by default. **Apply explicit frequency reference** sets a user-supplied anchor after FFT; it does not fit the display to an expected peak. Unsupported or missing filter metadata still causes a structured refusal. The [1D walkthrough](real-bruker-and-analysis.md) and [2D protocol](real-bruker-2d.md) fix source hashes, preprocessing and reference values. The per-axis first-point window scale defaults to 1.0; public 2D recipes use 0.5 and acquisition-derived broadening. Zero fill includes 8× for the 128-point indirect grid. With correction enabled, 1× restores the original direct grid after trim.

The **Analysis / figures** tab acts on the applied current result. Peaks/integrals use component 0. **Apply automatic phase (1D / 2D)…** fits all quadratures with a bounded positive-line model; 2D requires all four channels and estimates both axes jointly using centered point pivots. First-order estimation is optional and visual inspection remains necessary. HSQC uses zero-order; TOCSY uses first-order in the fixed public protocol. Per-axis corrections, pivot units, residuals and the 180° gauge appear in the summary and full saved JSON. Applied automatic corrections become explicit editable ordered steps, so the next Process replays them unless you remove them. Display-channel and source/result-view changes retain the digest-linked diagnostics. **Pick peaks** reports signed extrema, while **Integrate entered region** accepts one explicit inclusive point, Hz or calibrated ppm box at a time, with none, constant, edge-linear or reference-linear baseline choices. The results include flags and relative signed units. **Save analysis JSON…** keeps the complete report; **Save scientific figure…** writes SVG, PDF or PNG with an optional Matplotlib installation. Pending processing edits and previews are not included in the analysis.

For a full-size processed 1D/2D spectrum, show **Current**, zoom the applied spectrum, and choose **Use visible plot area as region**. This button is disabled for Original and Preview views; it refuses a stale displayed frame. You can also enter inclusive sample-center bounds on the applied spectrum in points, Hz or calibrated ppm and choose **Select entered analysis region**. **Analyze selected region of applied spectrum** then runs peaks or integration on the bounded view. Reports retain local region coordinates and absolute parent-spectrum points and coordinates. The selected region and reports survive session reopen. The whole-spectrum analysis cap remains in force; an oversized region is refused. Full-spectrum phase/noise/baseline JSON mask files are not interpreted as region-local masks; clear those selectors before a region analysis.

## Files and limits

**Open spectrum** accepts NMRNext native HDF5 and declared processed spectrum profiles. **Open acquisition folder…** detects supported acquisition directories, including controlled Bruker 1D `acqus`/`fid` and fully sampled 2D `acqus`/`acqu2s`/`ser` profiles. FFT of a filtered Bruker acquisition requires its explicit supported correction. Unknown/zero `GRPDLY`, DSP lookup/default correction, NUS and 2D modes other than FnMODE 5/6 remain unsupported. See [format profiles](formats.md) for the current exact scope.

Optional phase-anchor, noise-reference and baseline-reference JSON selectors use the same point-index region format as the CLI. Each selected file is interpreted against the current applied dataset; clear its path to remove it. For `reference_linear`, select samples outside the integration region that you have assessed as signal-free. See [analysis regions](analysis-regions.md) for syntax, assumptions and limitations.

When a frequency axis has no chemical-shift reference, the plot displays mathematical frequency offsets in Hz and says the reference is unknown. Confirm the frequency orientation and enter a known anchor explicitly before expecting physical ppm coordinates. The per-axis **Reverse frequency orientation when referencing** option reflects coordinates without reversing or conjugating the samples; leave it unchecked unless the acquisition convention calls for it. An editable zero in the reference field is a placeholder, not a value inferred from the acquisition. The quick controls use an exponential window; load an ordered recipe for a shifted-sine workflow.

The native HDF5 export preserves all components, dtype, axes, metadata and provenance. NMRPipe and UCSF exports write component 0 (the all-real quadrature channel) as float32. The workbench displays the exact preflight losses and requires an acknowledgment for each one before export. Preview results cannot be exported until processed. Existing files are never overwritten by the workbench.

Processed real files have no imaginary channel. Phase controls are disabled for those axes. If a selected recipe contains no operation, processing controls remain disabled while inspection and export remain available.

Scientific scope is limited to the implemented processor and file profiles. This interface does not provide general vendor digital-filter lookup, automatic phase beyond the bounded positive separable-line model, automatic baseline correction, 3D rendering, deconvolved peak fitting or full NMRPipe compatibility. The [Linux validation record](public-validation.md) covers prior published CI and the frozen 2D candidate's installed-wheel tests, both acquired controller pipelines and nine automated virtual-X11 groups, including recipe replay, diagnostics retention and normal console-window close. The GUI/plot/test environments were reused with the final wheel upgraded; the separate Qt/Matplotlib-free core environment was fresh. A human desktop session, GPU behavior, Wayland and researcher usability remain untested.
