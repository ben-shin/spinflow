# Validation and limits

SpinFlow's processing contract is described in [numerical conventions](numerical-conventions.md), [data model](data-model.md), and [format profiles](formats.md). The test suite includes independent direct-DFT and analytical fixtures, native versus NumPy comparisons, codec failures and read-back checks, CLI workflows, and optional GUI integration.

## Linux evidence

The tested source was the staged Git tree `282a6b4e2c95bb5f5bcc950e3306707e1f0c4cab`. It was archived and built in an Ubuntu 24.04.5 x86-64 guest with Linux 6.8, glibc 2.39, GCC 13.3, and CPython 3.12.3 under QEMU TCG software emulation. The build produced a native `spinflow-0.1.0-cp312-cp312-linux_x86_64.whl` (SHA-256 `55fb0d89c88bf29c8a475c71a7249a4deeaf74d86ed6c3c7495b3a4ec7390075`) and `spinflow-0.1.0.tar.gz` (SHA-256 `380d34fb60e3abbf94ee2f8c6c5e919ce97df2ba1d27c8ed4e954153eeb654f8`). A wheel was also built from the source distribution. The Linux bootstrap and in-place source extension helper completed.

In a fresh virtual environment with the Linux wheel installed, `pip check`, the installed-package CLI/native smoke test, and a GUI-inclusive test run passed **153 tests and 97 subtests**. The tests were copied away from a sibling `src` directory, and both `nmrnext` and its compiled `_native` extension resolved inside the installed environment. Twenty serial launches of the original real-Qt CLI path exited cleanly after a shutdown fix. A separate fresh headless wheel environment passed **139 tests and 85 subtests**, with exactly three real-Qt CLI tests deselected.

The source checkout was also tested with its matching in-place native extension. After `bash tools/bootstrap.sh --gui --test` and `.venv/bin/python tools/build_native.py`, its complete offscreen Qt suite passed **153 tests and 97 subtests**. A separate Qt-free Python 3.12 environment reused that helper-built source extension and passed the headless selection `--ignore=tests/gui -k 'not test_gui_'`: **139 tests and 85 subtests**, with exactly three real-Qt CLI tests deselected. These source runs used the same opt-in QEMU timeout factor described below.

The emulated source-suite commands were:

```bash
SPINFLOW_TEST_TIMEOUT_FACTOR=3 QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest -q
SPINFLOW_TEST_TIMEOUT_FACTOR=3 .venv/bin/python -m pytest -q --ignore=tests/gui -k 'not test_gui_'
```

These QEMU runs set `SPINFLOW_TEST_TIMEOUT_FACTOR=3` for three child-process startup guards that exceeded their original 3- or 4-second limits under emulation. The factor is an opt-in test-harness setting; it does not alter processing, parser behavior, or numerical acceptance limits. With the variable unset, the original deadlines remain in force, including in the configured GitHub CI workflow. The first unadjusted QEMU run had 147 passes and four failures: three startup timeouts and an intermittent Qt shutdown crash. The Qt lifecycle fix and repeated launch check addressed the crash; the subsequent installed-wheel runs passed with the stated timeout factor. This is not evidence that the complete suite passes under QEMU with default deadlines.

The earlier Windows x64/Python 3.13 preview passed 151 tests and 97 subtests after independent defect review; that is separate historical evidence. The [first GitHub Actions run](https://github.com/ben-shin/spinflow/actions/runs/40766518847) for commit `271f0f5ad830a13afea9d0f2666791c75527ae7b` completed successfully. On Ubuntu 24.04, the Python 3.12.15 and 3.13.17 headless jobs each passed **139 tests and 85 subtests** with three real-Qt CLI tests deselected; both built a native wheel and source distribution and passed isolated installed-package smoke checks. The Python 3.13.17 Qt offscreen job passed the complete source suite: **153 tests and 97 subtests**. That workflow did not set the QEMU-only timeout factor, so the original test deadlines applied. These results are specific to that GitHub runner and revision. Offscreen Qt checks do not establish physical desktop behavior or researcher usability; neither CI nor the emulated tests establish representative bare-metal performance.

## Linux GUI user-testing candidate

The Stage 10 executable source was frozen as Git tree `fa1e666bd9af6cc3ca6e6570b694919fbaa586cf` and archived with SHA-256 `3926affde28758df412639e03f11ebabdf11d6022526dc592c9ce90281a6c74d`. In an Ubuntu 24.04.5 / CPython 3.12.3 guest under QEMU TCG, it built `spinflow-0.1.0-cp312-cp312-linux_x86_64.whl` (SHA-256 `554f8963614df91b962d64266728b302ccd8d6dae575003a486812c648ac71c6`) and an sdist (SHA-256 `481d29f7bb849d76f95076d13d0c0c275bdd1466f749529202adf3bdf73b4db6`). In a fresh environment with only the wheel's GUI extra installed, `pip check` passed, pytest was absent, and the package plus compiled `_native` extension imported from that environment's `site-packages`.

Qt 6.12.0 loaded through its `xcb` platform plugin on a virtual X11 display (X.Org 21.1.11 and Openbox 3.6.1). The installed `spinflow gui` command opened a window and exited 0 through a normal Alt+F4 close. Automated QtTest interactions with real widgets and file dialogs passed ten workflow groups covering synthetic 1D/2D processing, distinct per-axis settings, preview/reset, plot zoom/components/resize, native save/no-overwrite/reopen, portable applied-workflow CLI replay with byte-identical numeric data and axes, export-loss cancel/acknowledge paths, and processed-real frequency crop. These checks used a virtual display and an automated operator; they are not an observation-based human usability session, a GPU check, or a Wayland test.

Separately, the revised native wheel was installed in an existing test environment upgraded to that exact wheel, and the tests were copied away from the source checkout. `pip check` and the complete installed-wheel suite passed **168 tests and 100 subtests in 92.63 seconds** with `DISPLAY=:99` and Qt's `xcb` platform selected. The QEMU TCG run used `SPINFLOW_TEST_TIMEOUT_FACTOR=3` only for the three known subprocess-startup guards; the normal CI deadlines remain unchanged. Some GUI lifecycle subprocess tests explicitly selected Qt offscreen within their own test commands. This result does not establish a full-suite pass under QEMU at default startup deadlines. The 66 archived public source files remained unchanged during Linux validation.

The Stage 10 numerical fixtures were synthetic, fully sampled mathematical examples. They do not prove correctness for general real vendor acquisitions or parity with NMRPipe. Stage 11 adds one bounded public raw Bruker 1D acquisition with a positive recorded digital-filter delay; the separate evidence below does not broaden that profile. Processed real NMRPipe/UCSF files are read back with the same nmrglue codec family plus byte-level tests, but have not been reopened in independent end-user applications. Lossy export requires explicit acknowledgment. GUI tests are automated; researcher usability sessions have not been completed.

## Stage 11 public acquisition and analysis candidate

The [public Bruker guide](real-bruker-and-analysis.md) identifies nine locally fetched, SHA-256-checked BMRB files and a recipe that explicitly corrects the recorded positive `GRPDLY` before FFT and anchors the frequency axis to archived acquisition/processing parameters. An independent archived TopSpin list supplies eight peak **positions**; the largest difference in this single acquisition was 0.001276 ppm against a 0.002 ppm tolerance. The comparison does not cover phase, amplitude, baseline, peak identity, integrals, an NMRPipe executable or independent export reopening.

The Stage 11 Windows/Python 3.13 source suite passed **328 tests and 100 subtests** with the public acquisition present, optional Qt and Matplotlib installed, `QT_QPA_PLATFORM=offscreen`, and ordinary startup deadlines. Separate CLI tests passed **32 tests and 4 subtests**, including versioned analysis reports, stale digest refusals, signed relative integrals, a supported 1,000-peak report consumed by figure export and proposal integration, and no-overwrite fault paths.

The frozen Stage 11 executable candidate is staged Git tree `a5241bde0969ae8322af336c541360f0d8c51a26` (82 public files). Its exact validation archive has SHA-256 `28b38e13fa6f266f51abb61b446fac39a6aff5fc148f6426f1204659b7f7d7d7`. Thirteen text archive members differ from their Git blobs only by CRLF/LF line endings; their normalized content matches. Historical checksum-backed numerical fixtures retain their exact bytes. The Ubuntu 24.04.5 LTS / Linux 6.8.0-147 / glibc 2.39 / CPython 3.12.3 / GCC 13.3.0 guest under QEMU TCG built a native `spinflow-0.1.0-cp312-cp312-linux_x86_64.whl` (SHA-256 `5e357d660a29c9bd795d4abda1b290dafb5c3fb3466301b88600fa28d87466dc`) and source distribution (SHA-256 `f7fdbeac247c40fbad2bdc6671966c6db8d277c852b9f7f79436f26bcaf7ff45`). These are local validation artifacts, not a published package release.

Three separate fresh installed-wheel environments checked the dependency boundary: core without Qt or Matplotlib; `[plot]` without Qt; and `[gui,plot]` for the desktop. The installed Python and native `.so` files in all three environments matched the built wheel's bytes. The Qt-free plotting environment ran the public Bruker 1D pipeline through the installed native backend and ten console commands, produced SVG/PDF/PNG figures and JSON/CSV reports, refused overwrite without altering an existing figure, and rejected inconsistent annotation coordinates. The nine public source files matched their pinned hashes before and after processing. The CLI replay's numerical samples matched the API processing result exactly.

For that Linux pipeline, a thresholded peak report found nine candidates and every one of eight archived TopSpin peak positions had a nearest candidate within **0.000205 ppm** (maximum observed difference 0.0002041724 ppm). In two chosen signal regions, the phased SpinFlow result and archived TopSpin processed real spectrum had a Pearson correlation of **0.97915928**; the baseline-corrected triplet/multiplet integral ratios were **1.988523804** and **2.008160481**, respectively. These descriptive comparisons use different apodization/baseline policies. They do not establish phase, amplitude, integral or concentration equivalence, assignments, NMRPipe parity or general Bruker support. The separate public recipe's magnitude-only maximum check remains the 0.001276 ppm result above; its processing and peak-selection protocol differs from this Linux analysis demonstration.

Qt 6.12 loaded with the `xcb` plugin on a virtual X11/Openbox desktop. A fresh `[gui,plot]` installed-wheel environment launched `spinflow gui` and closed through the window manager with exit 0. Seven automated QtTest workflow groups exercised the real acquisition, processing, analysis report retention across displayed components, figures and save paths. This was an automated virtual display session, not a human usability study, Wayland run or GPU check.

The full Stage 11 suite was copied outside the source checkout and run in a **separately reused test environment** upgraded to the exact candidate wheel; `pip check` passed and the package/native extension imported from its `site-packages` and matched the wheel's bytes. It passed **328 tests and 100 subtests in 140.10 seconds**, with no failures or skips, with X11 selected and the public files present. This QEMU TCG run set `SPINFLOW_TEST_TIMEOUT_FACTOR=3` for the three existing child-process startup guards only; numerical limits and scientific assertions were unchanged. It is not evidence of a default-deadline QEMU full-suite pass. The Stage 11 GitHub Actions workflow and Linux Python 3.13 matrix have not yet run for this candidate. The successful [earlier user-testing CI run](https://github.com/ben-shin/spinflow/actions/runs/40773797213) belongs to the prior commit.

The prior Windows benchmark is not a Linux performance claim. No NMRPipe runtime comparison, general speed ranking, hard process-memory bound, or out-of-core capability is established. See the [roadmap](../ROADMAP.md) for the validation still needed.
