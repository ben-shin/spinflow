# Candidate processing support contract

This is the **proposed** finite contract for a future scoped SpinFlow 1.0 processing release. Version `0.3.0b2` is an **experimental beta candidate**; the published `v0.3.0b1` beta and older `v0.2.0` prerelease remain immutable. The b2 change is a focused selected-region GUI figure export and qualification work; the processing algorithms, public numeric/recipe/session schemas and existing numerical gates are unchanged. Nothing in this contract declares 1.0 released, a profile stable, a researcher session accepted, or general NMRPipe parity. The machine-readable status and exact profile IDs are in [the support registry](../compatibility/support.json); the detailed restrictions are in [format profiles](formats.md), [data model](data-model.md), and [numerical conventions](numerical-conventions.md).

## Proposed finite 1D/2D promotion scope

The promotion target is reproducible, fully sampled **1D/2D numeric processing** through a headless CLI and optional Qt workbench on Ubuntu 24.04 x86-64, CPython 3.12/3.13. A profile becomes stable only after the corresponding scientific, workflow, installed-artifact and researcher acceptance gates pass. Current implementations remain experimental.

| Input/output profile | Candidate boundary | Key condition |
| --- | --- | --- |
| `nmrnext-hdf5` | Native schema-1 numeric 1D/2D storage | All declared quadrature channels, dtype, axes, JSON metadata and provenance retained; eager `Dataset` path has an explicit working-array budget. |
| `bruker-raw-1d` | Controlled complex `acqus`/`fid` | Supported endian/dtype/AQ modes, complete padded records and positive recorded `GRPDLY`; correction is explicit. |
| `bruker-raw-2d` | Controlled fully sampled hypercomplex `ser` | `AQ_mod=3`, `AQSEQ=0`, `PARMODE=1`, `FnTYPE=0`, `FnMODE=5/6`, positive recorded `GRPDLY` and declared digitizer/sweep checks. |
| `varian-raw-1d` | Unarrayed big-endian float32 `procpar`/`fid` | Explicit post-FFT Hz/ppm reference with `frequency_scale=-1` and a known anchor. |
| `varian-raw-2d` | Selected fully sampled `cpjdcptan2d` C13/N15 States `phase=[1,2]` case | Explicit reference on each frequency axis; broader vendor encodings are outside scope. |
| `nmrpipe-real` | Processed real 1D/2D read/write in the declared nmrglue 0.12 header dialect | Export selects component 0 as float32 and requires acknowledgment of every reported loss. |
| `ucsf-real` | Processed real 2D read/write, UCSF NMR version 2 | The same component projection and loss policy applies. |

The initial support target is the described *profiles*, not every file bearing a vendor or format name. The selected public Bruker cases and one previously studied Varian protein comparison are evidence for those cases; independent acquisitions per promoted profile and actual researcher acceptance remain release gates. Neither this target nor a 1.0 version number certifies universal scientific accuracy. Resource targets must be frozen and measured on the exact candidate; the 256 MiB default eager working-array budget and explicit block budget are planning controls, not hard RSS limits. Processing runs offline after installation. The target OS is the initial distribution scope, not a claim of tested macOS/Windows binaries.

`jcamp-real-1d` remains experimental because it has constructed fixtures only. The separate [bounded native-file mode](tutorials/bounded-block-processing.md) is also experimental: native schema-1 HDF5, one through four physical axes, fully sampled uncompressed/unfiltered storage, native backend and one thread. Its acquired 3D/4D examples establish selected numerical processing with **relative Hz** coordinates, not calibrated ppm assignments or processed-reference parity. It has no raw 3D/4D vendor importer, global high-dimensional analysis, lazy plane/strip GUI, digital-filter correction, or high-dimensional NMRPipe/UCSF export.

Assignment projects, chemical-shift lists, NEF/NMR-STAR interchange, legacy script migration, NUS reconstruction, whole-spectrum baseline correction, general vendor support, broad automatic phase, global high-dimensional analysis, and general NMRPipe speed or option parity are outside this scoped processing target. The historical `compatibility/functions.yaml` seed inventory is not a promise of equivalent commands.

## Public entry points and error behavior

The top-level Python package publicly exposes `Axis`, `Dataset`, `NMRNextError`, and `__version__`. Documented submodule entry points include `nmrnext.io` (`capabilities`, `describe_dataset`, `read_dataset`, `export_preflight`, `write_dataset`), `nmrnext.operations` (`apply_operation`, `run_operations`), `nmrnext.planning` (`plan_operations`), `nmrnext.analysis` (`autophase`, `pick_peaks`, `propose_regions`, `integrate_regions`, `dataset_digest`), `nmrnext.regions` (`select_analysis_region`, `pick_peaks_in_region`, `integrate_regions_in_region`, `verify_region_mapping`), `nmrnext.session` (`save_session`, `load_session`), `nmrnext.blocks` (`plan_file_operations`, `process_to_file`), `nmrnext.workflow_bundle` (`export_workflow_bundle`), and `nmrnext.support` (`support_capabilities`). The exact signatures are in those modules; this list identifies the intended compatibility surface, not every internal helper.

Both `spinflow` and `nmrnext` invoke the same CLI. Commands are `doctor`, `formats`, `gui`, `first-spectrum`, `demo`, `inspect`, `plan`, `run`, `convert`, `compare`, `autophase`, `peaks`, `integrate`, and `figure`. The parser in `src/nmrnext/cli.py` is the exact flag/default inventory. Promised command families and key flags are: `plan/run RECIPE [--backend native|numpy] [--threads N] [--memory BYTES] [--block-memory BYTES]`; `convert INPUT OUTPUT [--dry-run] [--allow-loss CODE] [--input-format ID] [--format ID]`; `autophase INPUT OUTPUT --report PATH` with axis pivots, masks and fit limits; `peaks` and `integrate` with signed/component selection, explicit bounds, baselines and reports; `figure` with optional plotting dependency. `--block-memory` selects the distinct native-file path and cannot be combined with `--memory`. Memory strings accept integer bytes or `B`, `KiB`, `MiB`, `GiB`, not decimal `MB`. `plan` checks headers and recipe geometry without sample validation; `run` validates samples. The CLI refuses overwrite by default. `--version` reports the package version.

`NMRNextError` is a `ValueError` with a stable `code`, `details` mapping and `to_dict()` shape. CLI domain errors are JSON on stderr and exit 2; cancellation exits 130. Unsupported versions, unknown recipe fields/operation parameters, unsupported formats, invalid budgets, nonfinite data, unrepresentable target headers and unacknowledged losses fail with named errors. Error *codes* and the JSON error shape are the compatibility surface; exact human message text is diagnostic and may change. No silent backend fallback, numerical alignment, unknown DSP lookup, or input overwrite is allowed.

The b2 GUI's **Save scientific figure** path can use a selected bounded region of the applied **Current** result, together with compatible local peak/integral annotations. The parent spectrum is retained and its phase report is separate workflow evidence. Original, Preview, stale or mixed region/report state, and an existing destination must be refused without replacing the prior good state. Unselected figures retain the existing four-million-sample guard. The large viewer remains sampled; adaptive viewport zoom is deferred. The [qualification protocol](v1-qualification-protocol.md) and [results](v1-qualification-results.md) distinguish source-host evidence from an installed b2 artifact. On that selected installed figure, PNG/PDF and the original SVG rendered in checked consumers with equal region/report linkage; QtSvg retained two warnings from empty contour paths with no observed drawing loss. This is a qualified reader check, not universal renderer or font fidelity.

## Saved recipes, numeric records and evolution

CLI recipes are JSON `schema_version: "1"`, at most 1 MiB, with `input`, `output`, `operations` and optional `backend`, `threads`, `memory_bytes`, `allow_losses`, `input_format`, `output_format`. Paths resolve relative to the recipe. Duplicate keys, nonfinite JSON, unknown top-level fields and unknown schema versions fail. Each operation is an object with `op`, optional `version` (currently string `"1"`), and only its declared parameters. The operation families are `digital_filter`, `reference`, `window`, `zero_fill`, `fft`, `phase`, `crop`, `reverse`, `transpose`, and `discard_imaginary`. The validator rejects unknown parameters and versions before executing a recipe. The beta GUI can load and edit an ordered recipe, preserve applied automatic-phase steps, and save a session with original native source snapshot, CLI workflow, selected analysis region and digest-linked reports. The published b1 evidence includes one acquired installed save/reopen and exact CLI replay; b2 installed and human workflow acceptance are separate gates.

The beta session API writes a new folder with `source.nmrh5`, `workflow.json`, and `session.json` in that order. `session.json` is the last commit marker; publication is sequential and **not an atomic whole-directory snapshot**. The loader checks source/workflow bytes and replayed numeric identity before returning a session record. A SHA-256 over cached report content detects accidental single-field changes; it is **not an authenticating signature** and does not independently recompute scientific results. The published b1 diagnostic and the private installed b2 cohort checked selected nested-report and acquired save/reopen workflows; human acceptance remains separate. Region bounds use inclusive sample centers in points, Hz, or calibrated ppm; their local points and parent-grid mapping are retained. See the [processing-session walkthrough](tutorials/processing-session.md).

Selected genuine Ubuntu b1 sessions reopened under installed Ubuntu b2 with exact samples, digests and cached reports; the recorded backend version changed only in explicit provenance fields. Source acquisition and native numeric file data can be read separately from a saved session, but cached-report replay requires exact numerical identity. Original Windows-created b1 diagnostic sessions refused under both Linux b1 and b2 after small cross-platform numeric differences, despite matching axes and quadratures. This is an observed portability limit, not a reason to weaken digest checks or silently accept a tolerance. It does not establish blanket cross-platform session compatibility; see the [b2 qualification results](v1-qualification-results.md).

Native schema-1 HDF5 stores `/data` float32/64 with shape `(2**q, *physical_axis_sizes)` and string root attributes `schema_version="1"` and `metadata_json`. Metadata has exactly `schema_version`, `axes`, `complex_axes`, `metadata`, `provenance`. Bit `k` selects the imaginary quadrature for `complex_axes[k]`. Axis coordinates are `start + step*index`; frequency is Hz, time seconds, ppm is `reference_ppm + (frequency_hz-reference_hz)/observation_mhz` when the reference is known. Native schema 1 retains every channel and numerical dtype. Unknown versions or malformed content refuse, rather than being guessed.

The [numerical contract](numerical-conventions.md) is versioned independently of the package number. Its version-1 forward FFT is unscaled and negative-exponent; inverse is scaled by `1/N`; output is FFT-shifted. Window broadening is Hz, phase `p0/p1` and automatic-phase corrections are degrees, pivot is a zero-based point, crop bounds are half-open point indices, and region reports use inclusive bounds with signed relative intensity·Hz (1D) or intensity·Hz² (2D). `reference.frequency_scale` defaults to +1; optional `reference.spectral_width_hz` means `N*abs(step)` of the **current** grid. Exponential window `lb_hz` defaults to 0, `first_point_scale` to 1, phase `p0/p1/pivot` to 0, `fft.inverse` to false. Analysis defaults are in `analysis.py` and the CLI parser; no auto phase fit is guaranteed to succeed on every spectrum. The `numpy` backend is explicit experimental bootstrap; native backend availability is checked and requested native execution cannot silently fall back.

For a future stable compatible release line, schema-1 recipes and native files made by a released compatible version should continue to load with the same numerical meaning for supported fields. A change that would alter coordinates, quadrature interpretation, output values beyond declared tolerance, loss meaning, or default processing requires an explicit numerical/operation version, provenance entry, and migration guidance. Additive optional fields can be introduced only when older artifacts retain their interpretation; writers must not silently emit a schema that supported readers cannot understand. Removing a documented command, flag, import or accepted profile requires a documented deprecation period in a compatible release and an explicit migration path; incompatible removal belongs to a major version. Unknown or unsupported content remains a structured refusal, not a lossy implicit conversion. These are **candidate policies**, subject to acceptance and implementation checks before a stable promise begins.

The archived v0.2.0 synthetic `process.json`, source and processed native files passed a hash-verified read-only load probe and b1 diagnostic installed replay. The replay matched all samples within the predeclared `1×10⁻¹²` tolerance, axes and quadratures; the only complete-metadata difference was the recorded backend software version. That proves only this saved synthetic case. A selected installed b2 replay also passed the same v0.2.0 gate; broader historical compatibility and cross-platform session behavior remain unverified. See the dated [b1 evidence](v1-candidate-results.md) and current [qualification status](v1-qualification-results.md).

Processed real exports are intentionally lossy when relevant: `quadrature_projection`, `float32_quantization`, `metadata`, `provenance`, `reference_fields`, `axis_annotations`. `export_preflight` reports required acknowledgments; the caller must name each allowed loss. Float32 overflow, unsupported dimensions, missing ppm calibration and unrepresentable target headers are fatal, even with acknowledgments. Output profile conversion can reverse sample order for descending target axes and make a documented odd-size NMRPipe half-bin carrier adjustment, without fitting or silent peak alignment. This contract promises explicit loss reporting, not lossless NMRPipe/UCSF round trips.
