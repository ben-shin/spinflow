# Stage 17 bounded block-processing protocol

This stage adds file-to-file processing of native schema-1 HDF5 data with bounded working arrays. The existing `Dataset`, `read_dataset`, `run_operations` and default CLI paths remain eager and immutable. A separate path/result report exposes disk-backed execution; no public `.data` property becomes a lazy array or memory map.

The [bounded-processing tutorial](tutorials/bounded-block-processing.md) gives the Python signatures, recipe and accepted CLI memory units.

## Additive interface and support matrix

The public entry point is `nmrnext.blocks.process_to_file(input_path, output_path, operations, *, backend="native", threads=1, memory_bytes=256*1024**2, input_format=None, output_format="native", overwrite=False)`, returning a JSON-compatible result/plan report rather than a Dataset. `plan_file_operations(input_path, operations, *, backend="native", threads=1, memory_bytes=256*1024**2, input_format=None, output_format="native", output_path=None)` performs scalar/header preflight without selecting samples. Providing `output_path` also checks actual target-filesystem space and aliases.

`plan` and `run` gain an explicit `--block-memory SIZE` mode using that working-array budget; simultaneous `--memory` is refused to avoid two competing limits. The explicit option overrides the recipe's eager `memory_bytes` policy, as an ordinary `--memory` override does for eager execution; there is no second hidden cap or automatic increase. Without the new option, current recipe schema, defaults, refusal behavior and eager execution remain unchanged. The selected mode and effective byte policy are recorded in the result. Native input/output aliases are normalized explicitly; an unsupported format is refused before payload reads or output creation.

| Item | Initial bounded profile |
| --- | --- |
| Storage | Uncompressed, unfiltered internal native schema-1 HDF5 float32/float64 dataset, contiguous or bounded chunks, shape `(2**q, *physical_sizes)`; one through four physical axes. All components retained unless an explicit existing loss operation says otherwise. |
| Components | Bit `j` means the imaginary quadrature of `complex_axes[j]`; physical transpose never reorders these bits. No quadrature inferred from physical axis order. |
| Arithmetic | Existing explicit window, zero fill, FFT/inverse FFT, phase and reference conventions. Every FFT slab contains its complete active axis; only orthogonal dimensions are tiled. |
| Layout operations | Crop, reverse, transpose and explicit version-1 discard-imaginary with canonical global-shape provenance. |
| Backends | Pinned native PocketFFT, one engine thread for the new bounded profile; the existing eager NumPy reference and eager thread policy are unchanged. |
| Output | Native schema-1 HDF5 only, with complete axes/metadata/provenance; contiguous uncompressed intermediate/output storage avoids uncontrolled write chunk/decompression caches. |
| Explicit exclusions | Raw vendor 3D/4D ingestion, NUS reconstruction, block digital-filter correction, automatic phase/analysis, NMRPipe/UCSF high-dimensional export, GUI lazy viewing and dimensions above four. Existing eager profile capabilities do not expand through this mode. |

## Bounded execution and memory accounting

Whole-recipe validation uses the existing metadata transition rules and backend validation before any numeric payload is selected. The planner produces per-stage input/output shapes, resolved operations, full-axis slab geometry, minimum single-line working bytes, chosen batch count, source chunk/cache reservations and temporary-disk inventory. It does not apply the old full-cube eager allocation estimate as the block budget.

Each arithmetic slab contains all component channels and the entire operation axis. Other dimensions use bounded rectangular selections. FFTs are never applied independently to pieces of the transformed axis. Zero fill/crop/reverse/transpose require explicit global-to-slab mappings. The engine calls the established sample arithmetic; a shared scalar operation-entry helper creates full-cube input/output shape, dtype, calibration and loss records. Block-sized shapes must never leak into canonical operation provenance.

The working-byte policy includes simultaneously live real input/output slabs, complex packing/result buffers, phase/window vectors, finite-check temporaries, conservative native FFT workspace, explicit raw HDF5 chunk-cache caps, the largest uncompressed input chunk and bounded metadata/control overhead. Filtered/compressed datasets are explicitly outside this first profile; their native filter workspace is not claimed bounded. Oversized uncompressed chunks are refused before reading rather than silently exceeding the cap. Intermediate/output stores are contiguous and uncompressed. Minimum full-axis memory is calculated first; a smaller budget fails with required/available bytes before any output or scratch dataset is created. No hidden full-cube array, global `asarray`, `[:]` selection, eager `read_dataset` or identity cache is permitted in this path.

This budget bounds the declared working arrays/caches; it is not a promise that interpreter, operating-system and HDF5 process RSS equal that number. Record the actual conservative factors and any excluded overhead. Source HDF5 metadata JSON remains subject to its existing 1 MiB bound; output metadata must remain readable under the same native format limits. The plan/result JSON must expose its accounting and refusals.

## Validation, source identity and lifecycle

Validate every input sample for finiteness in bounded slabs before the recipe can crop, discard or otherwise hide bad values. Preserve arithmetic finite checks after each operation, including intermediate results later discarded. Header-only planning remains explicitly payload-unvalidated. Stream required source/output hashes in fixed buffers and preserve normal input/provenance work inside the endpoint timing; file-backed execution cannot replace numeric identity with paths or stats.

Guard source stat/header identity before opening/reading and again before publication; validate opened storage against the planned header. Record source hash identity and refuse a changed source. No acquisition script is executed. Source and target aliasing is refused. Default output is no-overwrite, including a file appearing during the final publish race.

Temporary files are newly created, private and owned by this invocation under the target filesystem. Preflight a conservative current-plus-next-stage byte inventory, final staging/metadata allowance and actual free space before processing. Disk availability can change; allocation/write/flush/close failure must leave the prior input and any existing output intact, with no partially published target. Publish only a closed, validated final native file using the existing atomic no-overwrite/overwrite policy. Remove only known newly owned scratch files; never recursively delete a computed unverified path or touch historical evidence. Report any cleanup failure truthfully.

Each new writer retains its exclusively created, unbuffered binary descriptor. Identity is captured and checked from that handle, and the HDF5 file-object driver writes through the same owned object rather than reopening a destructive pathname. Handles close before publication and on failed execution. File-object control state is covered by the existing metadata/HDF5 fixed reserves; there is no additional Python file buffer. Numeric scan/copy selection uses O(rank) scalar traversal, preserving component-first C order without materializing all tile offsets. The successful API report's `elapsed_seconds` is calculated after cleanup and its `elapsed_scope` includes planning, validation, hashing, output close/publication and cleanup; fresh-command parent wall additionally includes process startup and final reporting/exit.

## Acquired and independent numeric evidence

The initial public-data search found official BMRB 5329 WR41 acquisitions: 3D HNCO with physical sizes approximately 35 × 40 × 512 and eight components, and 4D CCNOESY approximately 16 × 18 × 60 × 320 with sixteen components. These are candidate validation sources until exact archive/member hashes, acquisition encodings, metadata and conversion receipts are fixed. The evidence owner must verify dimensions from the real acquisition and preserve its public source/licence. Distinct acquired increments and quadrature channels must not be invented by repeating/tensoring a 2D spectrum.

Any offline conversion to native HDF5 is a separately identified evidence tool, not a new production vendor reader. Pin source archive/member hashes, procpar/pulse program, conversion source/version, byte order, component signs/order, units, coordinate/reference policy and resulting native identity. Label unsupported vendor/scientific generalizations explicitly. If one real acquisition or its independent interpretation cannot be established, report that exact validation gap rather than presenting synthetic 4D as acquired evidence.

Use small, non-repeated synthetic 3D/4D fixtures with odd/even and unequal axis sizes for independent direct-DFT and mapping checks. Retain the existing analytical float32/float64 tolerances and any reused acquired gates; no fitted alignment, scaling, sign selection, phase correction or relaxed tolerance. Establish new case/ROI coordinates, weak/strong selection rules and any new case-specific limits before candidate output inspection. Compare complete data/component/axis/metadata/provenance identities against unchanged eager execution and an independent reference where available. Large comparisons and coordinate checks must themselves stream rather than hide a full-cube allocation in the engine's measured worker.

## Measurement and release protocol

Freeze exact baseline/candidate source, wheel, installed module/native library, harness, acquisition/conversion/recipe and resource identities. Use one CPU/native thread and controlled numerical pools for both lanes, identical precision and physical guest limits. The eager reference may require an explicit 8 GiB working-array policy while bounded execution selects 64/128 MiB; these numerical allocation policies intentionally differ and must be reported, without claiming identical working limits. They are distinct from the identical physical guest RAM. Separate fresh-command end-to-end wall/CPU/RSS from warm API scopes. Include input validation/hashing, all scratch I/O, output close, output hashing and requested provenance in the complete file-to-file endpoint; report processing subscopes separately. Filesystem cache state is warm/uncontrolled unless separately established.

Run one warmup per lane/case, then at least seven alternating baseline/candidate pairs for acquired 3D and 4D cases and the fixed eager regression case, retaining all trials. Publish per-run values, median/range/inclusive IQR, paired ratios and fresh-worker lifetime peak RSS with its aggregation scope. Compare multiple declared block budgets and non-repeated acquired subcube sizes where feasible; padding and dimension changes must be identical between paired lanes and separately labeled. Do not infer large-dimensional scaling from tiled 2D or attribute traced Python allocations to process RSS.

The collected v2 RSS distributions use `wait4` on each actual CLI child and cover its complete fork-to-exit lifetime, including an inherited pre-exec launcher resident floor. The Python controller can retain earlier reports, so that inherited floor can vary during the sequential cohort. The frozen harness's statement excluding earlier resident state is too broad without this qualification; preserve its original bytes and all 112 observations. These values are not pure post-exec CLI peaks, incremental allocations or hard RSS limits equal to the working-array budget. They conservatively bound the large worker's post-exec peak; they do not establish small-control memory benefits or scaling. Separate instrumented API `/proc` VmHWM observations are corroborating single observations, not repeated CLI distributions. The [results](block-processing-results.md) retain this scope and the slower blocked endpoint timings; no floor subtraction or replacement measurement is applied.

Before publication, freeze one integrated candidate, run all appropriate old/new tests and acquired checks, then obtain three independent complementary jurors plus an independent judge. Reserve at most two consolidated post-review repair rounds for this Stage 17 deliverable. Gates not executed are UNVERIFIED. Git commit/push occurs only after root acceptance; verify every CI job against the exact published commit. Historical releases/assets stay unchanged.
