# First engine architecture

Python provides immutable numeric/axis objects, recipe validation, CLI, adapters and provenance. Operations share one engine across clients. C++20/pybind11/PocketFFT supplies the native FFT boundary: `_native.fft_complex(array, axis, inverse=False)` accepts complex64/128 and returns same-dtype unshifted output, preserving input. The Python engine assembles independent hypercomplex pairs and applies explicit centering. Selecting `native` must fail if unavailable; `numpy` is an explicit experimental bootstrap backend, not a hidden replacement.

HDF5 schema 1 is native storage; controlled NMRPipe and UCSF profiles are independent adapters. All writes use explicit output paths, no overwrite by default, temporary staging and atomic completion. Import never executes scripts. Runtime is headless and offline. The public project is SpinFlow; the existing Python module and primary entry point remain `nmrnext`, and `spinflow` is an alias. The native extension is built into platform-specific wheels. Original code is MIT licensed; dependency notices are separate. The machine-readable [support registry](../compatibility/support.json) separates source capability from the proposed 1D/2D processing release scope.

Eager operation API: `apply_operation(dataset, op, backend='numpy', threads=1)`, `run_operations(dataset, operations, backend='numpy', threads=1, memory_bytes=None)`. Planner validates the entire recipe using shape/axis metadata before work, estimates conservative array scratch requirements, and rejects an insufficient working-array budget. The public `Dataset` remains an eager immutable numeric result; its budget is not total process RSS.

The separate [bounded native-file path](tutorials/bounded-block-processing.md) exposes `plan_file_operations` and `process_to_file` for fully sampled, uncompressed/unfiltered native schema-1 HDF5 with one through four physical axes. It retains full transform lines and all quadratures while tiling other axes, uses the native backend with one thread, and publishes closed output atomically. Its declared working budget includes slabs, complex/native workspace, metadata, hash buffers and selected HDF5 cache reserves, but excludes interpreter/OS overhead. It does not make `Dataset`, GUI viewing, raw vendor 3D/4D input, global analysis or external high-dimensional exports lazy. Acquired 3D/4D evidence has relative Hz coordinates only.

Changes to the numerical contract need independent reference cases. The CLI, Qt viewer, and file adapters share the same validated core operations.
